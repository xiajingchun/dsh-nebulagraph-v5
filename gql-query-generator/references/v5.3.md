## Dynamic Label Expressions

Use a string `VALUE` or binding variable as a node or edge label expression when the label is selected at runtime.

```gql
USE <graph_name> {
  VALUE label_name = "Person"
  MATCH (v:label_name)
  WHERE v.id = <id>
  RETURN v.id, type(v)
}
```

The same pattern applies to edge labels:

```gql
USE <graph_name> {
  LET edge_types = LIST["KNOWS", "WORK_AT"]
  FOR edge_type IN edge_types
  MATCH (src:Person{id: <id>})-[e:edge_type]->(dst)
  RETURN type(e), type(dst)
}
```

Apply these constraints:

- Require a string-producing `VALUE` or binding variable. Do not use aggregators, files, tables, or numeric values as labels.
- Allow compound label expressions only when each operand resolves to a valid label name.
- Do not combine label and element-type expressions in one pattern: reject `(v:Person@Person)` and `-[e:KNOWS@KNOWS]->`.
- Treat a constant unknown label as an error. A runtime-computed unknown label can produce an empty result; do not promise compile-time validation for it.

## Dynamic Element Type Expressions

Use `@` when the intent is an exact element type, a type set, or type negation rather than a label expression.

```gql
USE <graph_name> {
  VALUE node_type = "Person"
  VALUE edge_type = "KNOWS"
  MATCH (src@node_type{id: <id>})-[e@edge_type]->(dst)
  RETURN type(src), type(e), type(dst)
}
```

Allow sets and negation, including dynamic operands:

```gql
MATCH (v@[type_a,TypeB])
MATCH (src)-[e@!excluded_type]->(dst)
```

Apply these constraints:

- Require each dynamic type item to resolve to a string through a `VALUE`, `FOR` variable, or `NEXT` output. Reject tables, aggregators, files, and non-string values.
- Use `@[Type1,Type2]` for a set and `@!Type` / `@![Type1,Type2]` for negation. The predicate forms `x IS ELEMENT TYPED ...` and `x IS NOT ELEMENT TYPED ...` follow the same type rules.
- Use `:` for labels and `@` for exact element types. Never combine both in the same node or edge filler.
- Prefer static type names when the type is known at generation time; use dynamic references only when runtime selection is part of the requirement.

## K-Hop Expansion

Use fixed chains when every intermediate node matters:

```gql
MATCH (a:Person{id: <id>})-[:KNOWS]->(b:Person)-[:KNOWS]->(c:Person)
RETURN DISTINCT c.id
```

Use an edge-following quantifier when only the endpoint or hop range matters:

```gql
MATCH (a:Person{id: <id>})-[:KNOWS]->{1,3}(d:Person)
RETURN DISTINCT d.id
ORDER BY d.id
```

Place `{lower,upper}` after the edge pattern and direction. Support lower bounds greater than one when requested, for example `{2,4}`. Add `DISTINCT` only when endpoint deduplication is part of the intent; cycles and multiple paths can otherwise repeat endpoints.

Do not emit Cypher quantifiers such as `[:KNOWS*1..3]`.

## Index Hints on Path Expansion

Preserve a user-provided VC index hint inside the edge filler, including quantified expansion:

```gql
MATCH (src:Person{id: <id>})
      <-[e:KNOWS WHERE e.creationDate >= <cutoff> /*+ INDEX(<index_name>) */]->{1,3}(dst)
RETURN count(dst)
```

Do not invent index names. Omit the hint when schema/index metadata is unavailable.
